# The P99 Worker

One Worker, one D1 database (binding `DB`), one R2 bucket (binding `BUCKET`) and one SQLite-backed Durable Object, `P99Hub` (binding `HUB`), per space: a space is the Cloudflare account P99 is deployed to. `p99 deploy` binds `SPACE` (the space's slug) and `SPACE_NAME` (its display name). The Worker is mounted on every host it serves as the route `<host>/_p99/*`, so a page talks only to its own origin. It may also sit on a custom domain of its own.

The host of a request is the URL's hostname. A host must be listed in the `hosts` table to be served; an unknown host answers 404 on everything but `/_p99/health`. The signed API is the exception: it names the host itself (below), so it answers on any address the Worker is mounted on.

## Paths

| Path | What |
| --- | --- |
| `GET /_p99/health` | `{"ok":true,"version"}`, unsigned |
| `GET /_p99/p99.js` | the loader |
| `GET /_p99/panel.js`, `/_p99/board.js`, `/_p99/avatar.js`, `/_p99/p99.css`, `/_p99/capture.js`, `/_p99/art/concrete.webp`, `/_p99/art/concrete-dark.webp` (and their `-2x` twins) | the lazy parts |
| `/_p99/api/*` | the browser API, authorised by a personal code |
| `/_p99/v1/*` | the signed API, for the CLI, the TUI and `p99 announce` |

Static files are answered from text modules bundled into the Worker (`worker/src/web/`). The loader is `Cache-Control: public, max-age=300`; every other file is fetched as `<path>?v=<version>` and answered `public, max-age=31536000, immutable`. `__P99_VERSION__` in any served file is replaced by the Worker's `VERSION` variable.

## Errors

Every error is `{"error":"<code>","message":"<English>"}` with 400 `invalid`, 401 `unauthorized`, 403 `forbidden`, 404 `not_found`, 409 `conflict`, 413 `too_large`, 428 `totp_required`, 429 `rate_limited`, 500 `internal`. A `client_uid` seen before answers the original object with 200, never a duplicate. The message is written for the person who reads it: the panel and the CLI show it as it is.

## The browser API

Every request carries `X-P99-Code: <code>`. A code is 12 characters of Crockford base32 (`0123456789abcdefghjkmnpqrstvwxyz`); the Worker lowercases it, reads `i` and `l` as `1` and `o` as `0`, drops `-` and spaces, and looks up its keyed hash, HMAC-SHA256 under the Worker secret `CODE_PEPPER`, so the `codes` table alone gives no code away (`p99 setup` makes that secret once and `p99 deploy` keeps it). A missing, unknown or revoked code, or one whose grant doesn't reach the request's host, answers 401, and the loader then forgets it; a parked code answers 403 on every route (see [Spaces, projects and grants](#spaces-projects-and-grants)) and is kept, since it is not revoked; a revocation takes effect everywhere within ten seconds. Each code is limited to 120 requests a minute (the `RATE` rate-limiting binding, when the Worker has one) and to the daily limits below. Both answer 429 `rate_limited`; a daily limit's message starts with `today's limit of`, and the panel shows it at once, while it retries the per-minute one, a 5xx and a lost connection a few times before saying so. Since the code travels in a header and never in a cookie, there is no CSRF surface.

A code with an authenticator (`totp`) answers 428 `totp_required` to every route but `POST /_p99/api/verify` until the browser holds a device token for it, and the header then carries both, `X-P99-Code: <code>.<device>`. The TOTP is RFC 6238 with SHA-1, 6 digits and 30-second steps; the Worker keeps its secret encrypted with AES-GCM under a key derived from `CODE_PEPPER`, accepts one step either side of now, never a step at or before the last one used, and after 10 wrong codes answers 403 until `p99 invites totp <id>` sets a new secret. Device tokens are 128 random bits, kept as keyed hashes in `code_devices`.

The actor of a browser request is the code's person: `{email, name, role}`. A person is an **Owner**, who runs P99 (triage, statuses, codes, boards; a space may have several), or a **User**, who signs in with a code to report and comment. An Owner is a code minted with `"role":"owner"`, or an e-mail in the Worker's `MANAGERS` secret (comma separated); every other code is a User. Answers carry `"role":"owner"|"user"` (`/me`, `/people`, a code object, a comment's author); `/me` and a code object also carry `"manager"`, true for an Owner, which the loader reads. **Changed in 1.13.0:** a body that sends `manager` answers 400 `manager is gone; send role: owner or user`. "Guest" is reserved for someone without a code, which no answer carries today.

### Usernames

Every person (an e-mail with a code, an e-mail in `MANAGERS`, an assignee) has a username, unique in the space: 3 to 30 of `a-z 0-9 . _ -`, starting and ending with a letter or digit, stored lowercase. P99 makes the first one from the person's name (`Zoë Ångström` is `zoe.angstrom`, then `zoe.angstrom2`), and the person changes it with `PATCH /me`. `admin`, `p99`, `root`, `support`, `manager`, `system`, `null`, `me`, `everyone`, `here` and `channel` are reserved, and a username is refused when, with dots, dashes and underscores taken out and look-alikes folded (`0` and `o`; `1`, `i` and `l`; `3` and `e`; `4` and `a`; `5` and `s`; `7` and `t`; `8` and `b`; `rn` and `m`; `vv` and `w`), it matches someone else's or a reserved word. An item keeps its assignee by e-mail, so a new username shows everywhere at once; every answer shows the assignee as `{"username"}`, never the e-mail. An agent acts as its person, so it has the person's username. The panel and the board draw each person's disc from the username with `/_p99/avatar.js`.

## The signed API

Every route under `/_p99/v1/` is signed:

| Header | Value |
| --- | --- |
| `X-P99-Key-Id` | the key id, `p99` |
| `X-P99-Actor` | base64url, no padding, of the actor JSON; absent only on `POST /_p99/v1/builds` |
| `X-Content-SHA256` | lowercase hex SHA-256 of the body (empty body: the hash of nothing) |
| `X-P99-Auth` | `v1 ts=<unix seconds>,sig=<hex>`, `sig = HMAC-SHA256(secret, "v1\n" + ts + "\n" + METHOD + "\n" + path_and_query + "\n" + X-P99-Actor + "\n" + X-Content-SHA256)`; refused when `ts` is more than 60 s away |

The secret of key id `p99` is the Worker secret `KEY_P99`, with `KEY_P99_NEXT` accepted beside it during a rotation. Key id `test` (the secret `KEY_TEST`) works only on `127.0.0.1` or `localhost`, for the Worker's own tests. There is no nonce: a captured request could be replayed within that minute, so the signed API travels over HTTPS only.

The actor is `{"email","name","agent"?}`, `agent` `true` when an agent acts as this person, left out otherwise. Items, comments and events keep it, and every view shows such an actor as the person's name with a robot, `Ada Lovelace 🤖`. An agent's label, `"via"`, comes back on the reporter, a comment's author and each event (`null` for a person's own action). The browser API never carries it.

**Key `p99`** is the space's own key, the one `p99 setup` makes and the CLI and TUI sign with. Its actor is always an Owner, so the daily limits never apply to it. It names the host with `?host=<host>` on any route (`host=*`, or no `host`, on the list and counts reads every host), and the environment with `env` in a build's body. On the list and counts an unlisted `host` answers 404; on an item's routes `host` is a filter, so an item of another host answers 404; `POST /_p99/v1/issues` takes the query's `host` first, then the body's.

## Live events

`GET /_p99/v1/stream` is signed like every other route, with an empty body, and upgrades to a WebSocket held by the Durable Object `P99Hub`, one per space. Every successful write sends each open socket one text message, a JSON event:

```json
{"type":"comment","key":"BUG-12","host":"shop.example.com","project":"Shop","space":"example","title":"The total does not update","by":{"name":"Ada Lovelace","agent":true,"via":"pci"},"at":"2026-10-15T09:30:00.000Z","internal":false}
```

| `type` | When | Adds |
| --- | --- | --- |
| `item` | an item is filed | |
| `comment` | a comment is added | `internal` |
| `change` | kind, assignee, title or body change | `what`, the fields that changed |
| `attachment` | a file is stored | `internal` |
| `import` | an import writes records | `items` and `comments`, the counts of new ones; `key` and `title` are null |
| `label` | an item's label changes | `from` and `to` (label names); `done` (`closed` or `reopened`) and `resolution` when its done-ness changed |
| `order` | an item is placed in its lane | `board` (the one board's id), `order` (its key there); `rebalanced` when the lane's keys were written afresh, which a reader takes as a reload |
| `labels` | a lane is renamed | `action` (`renamed`) and `names`, the old and the new; every socket hears it |
| `delete` | an item is deleted | `label`, the label it had; a `label` event back to the first label follows for each closed item that was merged into it |

A move's events carry the item's host. A reader patches its board in place on `label`, `order` and `delete` and reads it again on anything else.

`project` names the item's project (`null` when the event has none) and `space` the space's slug. `title` is the item's title after the change and `by` the actor, `null` for a write without one. Internal comments and files are included, since only the signed API listens. A socket opened with `host=<host>` hears only that host's events; an unlisted host answers 404. The socket answers the text `ping` with `pong`, which keeps it open through idle proxies; the CLI and the TUI send one every 30 seconds and reconnect when it drops. A Worker without the `HUB` binding (one not deployed since live updates came) answers 404 `this Worker has no push yet; run p99 deploy`, and its writes skip the event. The event is sent after the response, so a write never waits on it, and a socket that is not open misses it: a client that reconnects reads the list again.

## Items

- Keys are `<PREFIX>-<id>` over one sequence per space, the prefix from the kind: `bug` BUG, `feature` FEAT, `improvement` IMP, `question` Q, `task` TASK; any prefix with the right number, or the bare number, names the same item.
- Labels: an item carries exactly one label, its lane on the board (see Boards), and the seven lanes are the labels in use. A new item gets the first lane, `New`. The closing lane (`Done`) closes the item that carries it: it then has a `resolution`, `fixed` (the default), `abandoned` or `duplicate` (with `duplicate_of`); an open item's is null. The labels of the boards before 1.11 are deleted (see Boards).
- The status keys of P99 1.x and 1.8 still import, and still filter a list (`status=doing` keeps the open items in `In progress`): `new` and `inbox` are `New`, `confirmed`, `in_progress` and `doing` are `In progress`, `waiting` and `review` are `Landed`, `resolved`, `abandoned` and `duplicate` are `Done` with that resolution. Status events written before keep their old keys in `detail`.
- Owners change `kind`, `assignee`, `duplicate_of`, `resolution`, `title` and `body` with `PATCH`, and the label with `POST /move`; `labels` and `priority` answer 400. A 1.8 `status` still works: `done` (with `resolution`) closes the item, `inbox`, `doing` or `review` moves it to `New`, `In progress` or `Landed`, reopening it when closed. `resolution` closes an item (it goes to `Done`) and null reopens it (it goes back to `New`); setting `duplicate_of` alone closes it as `duplicate`. `assignee` is a username (a leading `@` is fine), `me` for the actor, or null, and the person must hold a live code reaching the item's project or be in `MANAGERS`; an assignee event's `from` and `to` are `{"username"}`. The reporter changes `title` and `body` while the item is in `New`, sets `abandoned` on an open item, and null to reopen a `fixed` one. A label change is an internal `label` event `{"from","to"}`; a change of what the reporter sees is a `status` event `{"from","to","resolution"?}` in their words; a `title` or `body` event keeps the old and new text as `{"from","to"}`, and neither mails anyone.
- `stage` is what a reporter sees: `received` while the item is in `New`, `in_progress` in any other open lane, then `fixed`, `dropped` or `duplicate` once closed; the panel words them Received, In progress, Fixed, Dropped and Duplicate. `label` is the label's name for Owners and null for anyone else.
- Everyone but an Owner sees only what they reported, and the items theirs were merged into; internal comments and their files are for Owners only.
- Attachments: 20 MB (20 MiB) each, 30 per item; roles `screenshot`, `page`, `region` (with `mark`), `file`; the type is the body's `Content-Type`, checked against the file's first bytes: PNG, JPEG or WebP for the images; for a `file` also GIF, PDF, `text/plain`, `text/csv`, `text/x-log`, JSON, zip, and Word, Excel, PowerPoint and OpenDocument files (`p99 file --attach` and `p99 comment --attach` pick it from the file's extension). A name ending in an executable or web page extension (`.html`, `.svg`, `.xml`, `.js`, `.exe`, `.bat`, `.sh` and the like) is refused, whatever the type.
- Limits per person and day: 30 items, 200 comments, 100 MB of files. Owners have none.
- Search (`q`) matches the title and body with accents and case folded on both sides (`cafe` finds `Café`): the Worker keeps `search_text`, the NFD form of title and body without combining marks, lowercased, and folds `q` the same way. `q` is matched whole, as one piece of text, and takes up to 200 characters, counted as Unicode code points (a single emoji is one, a flag two); `%`, `_` and `\` in it match only themselves. A `q` that is a key also finds that item. Text limits elsewhere (a title's 200 characters, a body's 20,000) count characters the same way.

A summary is `{"id","key","kind","stage","label","resolution","project","title","host","env","page":{"url","path","title"},"reporter":{"email","name","agent","via"},"assignee":{"username"},"created_at","updated_at","comments","attachments","unread","landing"}`; an issue adds `"body","duplicate_of","closed_at","context","marks","commits":[{"sha","subject","rel","envs"}],"github":[{"kind","rel","repo","number","url","at"}]` (`github` empty for anyone but a manager), and a thread's issue `"merged":[{"key","title","host","reporter"}]`, the items merged into it (for anyone but a manager, only their own); a comment is `{"id","client_uid","author":{"email","name","role","agent","via"},"body","internal","created_at","attachments":[id]}`; an attachment `{"id","client_uid","role","mark","name","type","bytes","sha256","comment_id","created_at"}`; an event `{"actor","actor_name","agent","via","kind","detail","at"}`, `actor_name` the person's name as the thread, or else the newest code for that e-mail, knows it (null for P99 itself), `agent` true when an agent acting as that person made it; `agent` is always a boolean, and `via` the agent's label, or null for a person and for an agent with none. `assignee`, the reporter's `email`, event actors' e-mails (and the `from` and `to` of an assignee event) and a comment author's `email` show to managers only: for anyone else they are null, unless they are that person's own. `project` is the name of the item's project, a report's (its host's) and a card's alike, for a manager, and null for anyone else; an item in no project says null. Every `assignee` also carries `"avatar"`, the person's avatar URL or null.

## Boards

A space has one board. Its seven lanes are its columns, by position: `new`, `planned`, `in-progress`, `needs-you`, `stuck`, `landed` and `done`, named `New`, `Planned`, `In progress`, `Needs you`, `Stuck`, `Landed` and `Done` until an Owner renames them. Every item, a plain item or a card, sits in one lane: a new report in New, a closed item in Done. An item's place in its lane is its priority, one order for the whole space. Owners see the board; a User's code answers 403. An Owner whose code reaches only some projects sees only the items it reaches.

- `GET /board` answers `{"board":{"lanes":[{"word","label","closes"}]},"cards":[card]}`, in lane order and then in each lane's order. A card here is `{"key","kind","project","status","label","lane","title","host","assignee","order","changed_at","changed_by"}`: `project` is the name of the item's project, a plain item's (its host's) too, and null only for an item in no project, `status` the lane's word, `label` its name, `lane` the item's place in its lane from 1 (null in Done), `assignee` a username or null, `order` its fractional key (a short base-62 string that sorts as text, null for an item not placed yet, which sits at the top of its lane, newest first), and `changed_by` a person as in a card. The filter: `project=` (repeatable; plain items then drop out), `host=`, `source=human` or `agent` (who made the last change), and `status=` (a lane word, repeatable).
- `POST /move` takes the item's `key`, `from` (the lane the mover saw, by word or name) and `to` (a lane word, or a lane's name matched with case and accents ignored); `board` is ignored. Any Owner moves any item they see. When the item isn't in `from` any more the answer is 409 `{"error":"moved","message":"this card moved; refreshed"}` and nothing changes. A move into another lane puts the item at the top of it; `before` or `after` a neighbour's key in that lane places it there. Placing writes one key for the moved item, between its neighbours' keys; the lane's keys are written afresh only when a key would pass 50 characters, or to place an item above items with no key yet. Done closes the item (`resolution` picks `abandoned` or `duplicate` over `fixed`); any other lane reopens a closed one. An agent can't move a card into Done (403 `only a person closes a card`). The answer is `{"card":{"key","kind","title","label","assignee":{"username"}|null,"order"}}`, and the move is one write and one broadcast: a `label` event, and an `order` event when it was placed.
- `GET /labels` answers the lanes, `{"labels":[{"id","name","word","closes","boards"}]}`, and `PATCH /labels/{id}` with `{"name"}` renames one (1 to 32 letters, digits, spaces or `. _ : + -`); a name another label holds is 409, an id that isn't a lane 404. The lanes are the space's: an Owner whose code reaches only some hosts can't rename one (403).

**Changed in 1.11.0:** each Owner's own boards folded into the one board. `0016_one_board.sql` does it once, and `p99 deploy` runs it only with `--accept-plan` (`p99 migrate --plan` shows it first). An item already in a lane stays there. Otherwise a closed item goes to Done with its resolution; an open one goes to New from Inbox, to Landed from Review, to In progress from Doing, and from any other label to In progress, so a reporter's stage stays as it was; an open item never goes to Done. Each moved item gets one internal `label` event `{"from","to","migrated":true}` with no actor, so its thread shows the old column's name and nothing counts as a change. Each lane keeps the order the items had on the oldest Owner's boards, then on the other boards in the order they were made, then newest first. 1.11.0 kept the old boards and labels archived; `0017_delete_archived.sql` (below) deletes them. A Cards board with six lanes gets Needs you as its fourth; a Cards board with any other number of columns, or six with one already called Needs you, is set to the seven lanes by name, and a card on a column that isn't one of them moves as any other item does. **Changed in 1.13.0:** `GET /boards` and `GET /boards/{id}` are gone and answer 410 `boards are one per space; see p99 board`, as `POST /boards`, `PUT /boards/{id}` and `DELETE /boards/{id}` do.

**Deleted after the fold:** nothing is archived. `0017_delete_archived.sql` runs after 0016, in the same deploy for a space still before 1.11, and like it only with `--accept-plan`. It deletes every old board with its columns and its order, every label that isn't one of the seven lanes, the old tags (rows from before 1.9 that nothing reads), and the archive 1.11.0 kept. What the one board doesn't hold yet is carried onto it first, and `p99 migrate --plan` lists each as a decision: an item still on an old label moves to In progress, or to Done when it is closed, with one `label` event `{"from","to","migrated":true}`; an item with a place only on an old board gets one after its lane's last card; either way in the order of the old boards, oldest first. Each item's history stays. On a space whose Cards board doesn't have seven lanes, the plan says so and deploy stops before any migration, deleting nothing. The plan also counts the items, comments, attachments, events and each lane's items before and after; `p99 deploy` sends its migrations as one step, counts again inside 0017 and, if any count differs, rolls every one of them back (0016 included) and stops, leaving the database as it found it. Running it again changes nothing.

## Cards

A card is an item filed or named into a project from the CLI or by an agent (or given one with `PATCH`), a name of 1 to 40 characters matched without regard to ASCII case; a report filed on a host is in that host's project too, and its JSON says so, but it stays a plain item, not a card. A card names a project that exists and that the code reaches; a code for the whole space (the key, or an Owner's code granted the space) that names a new one makes it with that spelling, as `POST /projects` does, and any other code answers 404. A card filed from the CLI or an agent needs no host: its `host` is then null. The `project` filter (`project=`, repeatable) on `/board`, `/cards` and `/issues` keeps the items in those projects, plain items included on `/board` and `/issues`. Only Owners see and change cards, on the signed API and the browser API alike; a reporter's code answers 403 on every card route.

The Cards board is the space's one board (see Board). Its seven lanes are the labels `New`, `Planned`, `In progress`, `Needs you`, `Stuck`, `Landed` and the closing label (`Done`), and the status words name them by position: `new`, `planned`, `in-progress`, `needs-you`, `stuck`, `landed`, `done`. Lanes are renamed as labels are; the words stay. Only the Done lane closes, whatever another lane's `closes` flag says.

- `GET /cards` lists in lane order, then each card's place in its lane; with no `status` it lists every lane but `done`. `project` and `status` repeat; `since` is an RFC 3339 time and keeps the cards changed at or after it; `source=human` or `agent` keeps the cards whose last change was a person's or an agent's; `host` keeps one host's; `limit` is 200 by default and at most 500, and `next_cursor` reads on.
- `GET /cards/waiting` answers `{"count":n,"cards":[card]}`: the cards in `needs-you`, `stuck` and `landed` that the reader sees, newest change first, up to 500, with `count` the whole number. `/me` carries the same number as `counts.waiting` for an Owner, and `null` for a User.
- `POST /cards/{key}/status` moves the card to that lane, at its top; a card already in it keeps its place. `done` closes it (`fixed`) and any other word reopens it. A note is a comment in the same write and mails no one. Anyone but a User may set `needs-you`, an agent included.
- A card in `needs-you` goes back by itself when an Owner (a person, not an agent) comments on it, internal or not, by `POST /cards/{key}/comments` or `POST /issues/{key}/comments`: in the comment's own write it moves to the top of the lane its last move came from (the `from` of its newest `label` event that the fold didn't write). When that lane is gone by a rename, or it was `needs-you` or the closing lane, the card goes to In progress. An agent's or a User's comment leaves it where it is, and any status set moves it as usual. Plain items in the lane stay put.
- A card's close by any other route (`PATCH` `status` or `resolution`, a merge, GitHub) takes it to the Done lane, and a `PATCH` `status` of `inbox`, `doing` or `review` to New, In progress or Landed.
- An agent (`agent` true in the actor) may close a card as `abandoned` or as a duplicate of another item (`PATCH` with `resolution: abandoned` or `duplicate_of`, or a merge); the card's `changed_by` then names the person with `agent` true. Closing a card as done stays a person's word: an agent's `status: done`, move into the closing lane, or `PATCH` that closes it `fixed` is refused with 403 `only a person closes a card`, and nothing is written.
- `PATCH /issues/{key}` with `project` alone gives an item a project, renames it, or with `null` takes it away. The item stays in its lane, open or closed, with its place on the board: a project change is one internal `project` event `{"from","to"}`, and it never mails, never reopens and never shows to the item's reporter. An agent sending `null` for a card is refused: 403 `only a person turns a card back into an item`.
- A plain item on a card route answers 409 `<KEY> is not a card; give it a project with p99 edit <KEY> --project <name>`; an unknown key 404 `no item <KEY>`; a bad name 400 `a project name has 1 to 40 characters`.
- A link is a `link` event, `{"ref","note"}`: `ref` 1 to 200 characters, `note` up to 200 (a blank one is null). A lane change stays a `label` event.

A card is `{"key","kind","project","status","label","lane","title","host","reporter","created_at","changed_at","changed_by","comments","links":[{"ref","note","by","at"}]}`: `status` the lane's word, `label` the lane's current name, `lane` the card's place in its lane among the cards the reader sees (1 is the top, null when done), `changed_at` and `changed_by` the card's latest event. Every person in it is `{"name","username","agent","via","avatar"}`, `avatar` the person's avatar URL or null, so a page draws the picture without asking for it; e-mails never appear.

**Changed in 1.9.0:** a summary, an issue and a card no longer carry `status`, `board`, `position`, `priority` or `labels`; they carry `stage` and `label`. `/statuses`, `POST /labels`, `DELETE /labels/{name}` and board slugs are gone; boards are named by id.

## Merging duplicates

`p99 merge BUG-14 BUG-15 --into BUG-12` folds reports of the same thing into one item. Each merged item gets `duplicate_of` the target and closes with resolution `duplicate` (a status event and a live `label`), with a `merge` event on it (`{"into"}`) and on the target (`{"item"}`), and its reporter is mailed the status change. Items already merged into a merged item move to the target too, so a merge stays one level deep; a target that is itself merged answers 409 and names the one to use. An Owner scoped to one host (`?host=`) merges that host's items only: an item on another host answers 404. Without `host`, items of several hosts merge.

Every reporter of a merged item follows the target: it shows in their "mine" list and counts, they read its thread and comment on it as any reporter does, and they are mailed its replies, status changes and landings. A follower sees the target's title, status, public comments with their files, events and landings; never its internal notes, its reporter's e-mail, text, page context, marks or capture files. Only the target's own reporter changes or drops it. `p99 show` and the TUI's thread list the items merged into an item, and the panel shows "merged into BUG-12" on each merged one.

## Deleting an item

`p99 delete BUG-12` (or `DELETE /issues/{key}` on either API, Owners only) removes an item for good: the item, its comments and internal notes, its events, read marks, labels, its place on its board, its GitHub links (GitHub's own issue and pull requests stay as they are), mail opt-outs, landings, and every file in the bucket, screenshots, page captures, marked areas and attachments, on the item and on its comments. There is no undo and no trace in the space but the Worker's log line, `deleted BUG-12 by Ada Lovelace 🤖`.

The rows go in one D1 batch, which is one transaction: a failure part-way leaves the item whole. The same batch records every file's bucket key in `deletions`; the files are then removed from R2, up to 1,000 keys a call, and each key is struck off once its object is gone. A key whose removal fails stays in `deletions`, and the cron trigger retries it every 15 minutes until it goes, so no file is left behind; a file still uploading when the item went is removed once more 15 minutes later. `retrying` counts the files still waiting.

Items merged into the deleted one lose their `duplicate_of`; a closed duplicate goes back to `New`, open (a status event on it, and a live `label`), so its report is triaged again. Keys are never handed out again, after a restore included: an item's number comes from SQLite's `AUTOINCREMENT`, which never reuses one, and the backups keep its counter for a restore to write back (see Backups). Chat hooks and GitHub get nothing, and no one is mailed. The fixed feed reads the current rows, so a deleted item drops out of it. The weekly backups in the bucket keep the item until they age out, eight weeks later.

## Environments and landings

An environment is a name with a kind. A `development` environment counts the build of branch `main`; a `release` environment counts its latest announced build, whatever the branch. `p99 announce` (or a host's own build) posts a build with the items its commits name in `Fixes:` and `Refs:` trailers; an item lands in an environment when a counted build there carries a `Fixes:` commit for it, or when an import records a landing there, and the first landing is an event. An environment with `notify` mails the reporter at an item's first landing there, when mail is set up.

`landing` is `{"branch":bool,"envs":[{"env","kind","at","sha","version"}]}` in `position` order, `branch` true when a fix sits only on a branch no counted build carries.

## The fixed feed

Off by default. `p99 feed on <host>` sets the host's `feed` and `https://<host>/_p99/feed` then serves an Atom feed (`?format=json`: a JSON Feed 1.1) of the host's items whose fix reached a `release` environment, newest first, at most 50: each entry carries the key, the kind, the title and the date of the first landing, and nothing else (no reporter, text, page, comments or commits). Anyone may read it, the response is cached at the edge for five minutes, and a host without `feed` answers 404. `p99 feed off <host>` turns it off; `p99 feed` lists each host's feed.

## Mail

Off until `p99 email set` turns it on for the space: the sender and the provider live in the database's `mail` table, and the provider's key in the Worker's secret `RESEND_API_KEY`. A Worker set up before that, with a `MAIL_FROM` binding and no `mail` row, keeps mailing from that binding until `p99 email set`, `p99 email off` or the next `p99 deploy` writes the row. Resend is the one provider; the Worker sends through one interface, a batch of `{to, subject, text, html}`.

New items and comments by anyone but an Owner go to every Owner. The reporter, and every reporter of an item merged into it, is mailed about an Owner's non-internal reply, the item closing or reopening, and the first landing of a fix in a `notify` environment ("fixed and shipped"); a merge reads as "merged into BUG-12". A change reads as the reporter sees it: Received, Fixed, Dropped or Duplicate. Other label changes mail no one. An Owner's own new item mails nobody, and no one is mailed about their own action. Every mail has a plain-text part and a light HTML part in the host's theme colours (`accent`, `on-accent`, `ink`, `muted`, `rule`), so subjects and bodies keep their accents; an agent acting as a person reads as `Ada Lovelace 🤖`. Sending never fails a request; each send, or skip, is an internal `mail` event with its outcome.

An Owner's link is `https://<item's host><page path>#p99=<key>`, which opens the panel on that item. A reporter's link is `https://<item's host>/_p99/open?to=<page path>&item=<key>#<their code>`: a small page on the host stores the code where the loader looks for it, the way an invite link does, and moves on to the page with the item open in the panel. The code rides in the fragment, which the browser never sends. The Worker keeps an AES-GCM sealed copy of each code for this (its key derived from `CODE_PEPPER`), written when the code is minted, or for an older code the first time it is used; until then that person's link has no code. No API answer carries the sealed copy.

Every mail to a reporter ends with a link to stop mail about that item, `https://<item's host>/_p99/mail?t=<token>`, and carries it as `List-Unsubscribe` with one-click `List-Unsubscribe-Post`. The token is signed for that item and that e-mail (HMAC-SHA256 under a key derived from `CODE_PEPPER`), so it works for nothing else and needs no code. Opening it stops the mail and offers Undo; the person still gets mail about their other items.

## Chat hooks

Each host may hold one Slack and one Discord incoming webhook (the `hooks` table). A `url` is taken only when it is `https://hooks.slack.com/services/<a>/<b>/<c>` or `https://discord.com/api[/v<n>]/webhooks/<id>/<token>` (or `discordapp.com`), with no port, user, query or fragment; anything else answers 400, so a hook can reach no other address. The URL is stored sealed with AES-GCM under a key derived by HKDF from `CODE_PEPPER`, as the authenticator secrets are. `events` defaults to all four on a new hook and is kept when a later `PUT` leaves it out.

After the response, in `waitUntil`, the Worker turns the request's live events into posts: `item` is `new`; a `comment` that is not internal is `comment`; a `label` change that closes or reopens the item is `status` (other label changes post nothing); a first landing in a `release` environment is `shipped`. Each hook gets one message per request listing up to ten items, Slack as `{"text","blocks"}` and Discord as `{"content","embeds","allowed_mentions":{"parse":[]}}` with the host's `theme.accent` as the embed colour. Each item shows its key, kind, title, label, the actor (an agent as `Name*`) and its page link (`https://<host><path>#p99=<key>`); never an e-mail address, a comment body or an attachment. A post has 5 seconds, follows no redirect, and its outcome is kept as `last_status`; a failure is logged and never fails the request.

## GitHub

`POST /_p99/v1/github` is GitHub's webhook, not signed with the space's key: the host is the URL's, and the body must verify against `X-Hub-Signature-256` (HMAC-SHA256 with the host's webhook secret) or the answer is 401. A delivery id (`X-GitHub-Delivery`) is acted on once. From the host's linked repository, a `pull_request` opened, edited or reopened records the items its title and description name in `Fixes:` and `Refs:` trailers; one closed as merged also reads its commits, records them, and moves every open item named in `Fixes:` to done with the resolution fixed, with the status event, the live event and the reporter's mail. An `issues` closed as completed (`state_reason` `completed`, or none) does the same for the item `POST /_p99/v1/issues/{key}/github` opened it for. Only items of that host are read or changed. The answer is 200 `{"linked":[key],"changed":[key]}` when something was recorded or changed, and 204 for everything else.

The host's secrets are Worker secrets named after the first 16 hex digits of the SHA-256 of the host name, uppercased: `GITHUB_TOKEN_<tag>` (the fine-grained token) and `GITHUB_HOOK_<tag>` (the webhook secret). `p99 github set` writes both. Links are kept in `github_links` and shown on an issue as `github` to Owners; `github_deliveries` keeps delivery ids for 30 days.

## Backups

The cron trigger (`*/15 * * * *`) runs a weekly backup of every table into the bucket under `backups/<date>/`, in steps small enough for one invocation, keeping eight. A deleted item stays in the backups taken before its delete until they age out; P99 never edits a backup.

A backup is one cut, taken when its run starts: rows written after that moment, such as an item filed while the run pages, its comments, files and events, wait for the next run. Tables are paged parents first (labels, boards and their columns, then items, then what hangs off items, codes before their authenticator devices, the key counters last), so a row deleted while the run pages is either in the backup with what points at it, or gone with it. A row that points at a label or a board made during the run (an item moved into a new column) brings that label or board along as one more page of its table. Two cases are cleared and named in the Worker's log line when the run finishes: an item merged into one with a higher key that was deleted before its page loses its `duplicate_of` (the delete does the same in D1), and a row whose label or board no longer exists is left out. Rowids of tables without `AUTOINCREMENT` can be handed out again after a delete, so in those tables a row added during the run can still land in the backup; it never points at a row the backup lacks.

Each page is `<table>-<page>.json` (`run`, `exported_at`, `table`, `page`, `rows`), where `run` is the run's start; a date's pages are a backup once that date's `backup_runs` row has `finished_at`. A second run on the same date replaces the first whole: it starts by replacing the date's `backup_runs` row, and before it finishes it removes every page the first left. Sign-in tries, app sessions, usage, GitHub delivery ids and the runs themselves stay out of the backup.

P99 has no restore command. To restore by hand into a freshly migrated D1, write each table's rows from its pages, `rowid` aside (`_rowid` in a page), and the `sqlite_sequence` rows too, replacing each row by its `name` (`DELETE FROM sqlite_sequence WHERE name = ?` then the `INSERT`), so a key used before, a deleted item's included, is never handed out again. Writing `sqlite_sequence` through `wrangler d1 execute` is built but untested on a real D1; if D1 refuses it, `UPDATE sqlite_sequence SET seq = ? WHERE name = ?` after the rows are in does the same.

## Schema

`worker/migrations/` holds the schema: `0001_p99.sql`, then each change in its own numbered file. Migrations are recorded in `d1_migrations` (`id`, `name`, `applied_at`), the table wrangler keeps, so a database migrated by either stays in step.

## Host config

`PUT /_p99/v1/hosts/{host}`'s `config` is `{"theme":{…},"strings":{…},"corner","offset":{"x","y"},"above","off":[…],"feed","mask":[…],"capture"}`, as docs/hosts.md describes. `mask` lists at most 50 CSS selectors of at most 200 characters each, and a selector that doesn't parse as a selector list answers 400; the panel masks every element they match in a capture, beside those marked `data-p99-redact`, unless the person filing unchecks "Hide this site's private areas" (password fields stay blanked). `capture` is `on` (the default) or `off`: on an `off` host the panel files the report without a screenshot, and the Worker refuses a `screenshot`, `page` or `region` attachment on that host's items with 403, so nothing of the page is stored even by an older panel. The Worker writes the host's `corner`, `offset`, `above`, `off` and `theme.accent` into the loader it serves for that host (replacing `__P99_HOST__` with that JSON), so the button draws in place before any request; `/_p99/api/me` answers the whole config.

## Spaces, projects and grants

A space holds projects, each with a name unique in the space (ASCII case ignored), and every host belongs to one project. A report filed on a host lands in that host's project; a card names its project. Each item keeps its project as `project_id`, and a card also keeps the name in `project`, kept in step on every write.

A code grants the whole space (`{"space":true}`) or some projects (`{"projects":[…]}`), never hosts. It reaches a host when it grants the host's project or the space, and it reaches an item in a project it grants; an item in no project it reaches through the item's host. A card on a host it reaches but in another project stays out of reach. Only `{"space":true}` reaches the whole space: a code granted every project today makes no project and reaches none made later. When a code's grant changes, or a host moves to another project, the open live boards it touches close, and the page opens them again with what the code now reaches. The P99 page opens on the space even when no project the code reaches has a host yet: `/me` then says `host` and `project` null, the board and cards answer as usual, and a report, which needs a site, answers 400. A parked code (`{"projects":[]}`) reaches nothing: the browser API answers it 403 `a parked code opens nothing; …`, and since it is not revoked, the browser keeps it. Moving a host to another project, or adding one, reaches everyone granted that project at once. No grant change, park or host move ever mails anyone. Owners are mailed about the items their grant reaches; an assignee is a person whose live code reaches the item's project.

## Licence

The licence state is read from a key an Owner pasted (`PUT /licence`, kept in the `settings` table) first, and from the deploy's `LICENSE_STATE` and `LICENSE_LINK` bindings after. A Studio or Agency key covering the Worker's build date gives `licensed: true` in `/me`, and the panel then hides its small P99 logo; an Agency key lets a host hide the "by PITO.MD" link.
